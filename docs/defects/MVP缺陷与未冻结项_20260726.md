## D-MVP-4：48 GPU 小时可行性已完成冻结前吞吐校准（2026-08-03）

v1 smoke 训练记录 14.835 秒，probe 记录 20.220 秒，累计 0.009737 GPU 小时。按 pilot
更新批次数做极乐观外推，训练与 probe 合计约 26.7 GPU 小时；按训练样本吞吐外推，仅训练
已约 48.3 小时。pilot 模型更宽、更深，因此完整 pilot 前必须使用等价规模的短时吞吐校准
和提前停止预算。该项冻结前短时校准现已完成，但正式运行仍以实际 `budget.json` 复核。

2026-08-03 用 `scripts/throughput_calibration.py` 在 RTX 4090（torch 2.12.1+cu130、
deterministic_algorithms 开启）以 pilot 模型规模与 batch 形状完成实测：120 个训练
cell、每 cell 3,900 步，完整 pilot 训练矩阵外推为 **fp32 3.08 GPU 小时**（bf16 autocast
反而 3.52 小时——该规模模型是 kernel 启动延迟瓶颈而非算力瓶颈）。此前 48.3 小时的
悲观外推源自 DataLoader 数据管线开销，已被 D-MVP-19 的 gpu_resident 后端消除。结论：
48 小时预算下单次完整 pilot/formal 运行（训练 + probe）预计 4–6 小时，允许多次完整
重跑；正式运行后仍需以实际 budget.json 复核本外推。

## D-MVP-8：首次运行暴露 Windows 启动前检查问题

2026-07-31 的首次调用确认了三个启动层问题：

- 项目 `.venv` 尚未创建；当前 Conda base 的 Python 3.12.8 可作为创建它的解释器，
  但 `py` 启动器仅注册了不受项目支持的 Python 3.13；
- 旧脚本包含无 BOM 的 UTF-8 中文异常文本，在部分 Windows PowerShell 配置中显示为乱码；
- 旧脚本未显式检查原生 Python 进程的退出码，在 Windows PowerShell 5.1 中存在失败后继续
  执行同阶段后续命令的风险。

脚本已改为纯 ASCII 启动错误信息、明确的 3.11/3.12 环境创建指引、配置存在性检查和
逐命令退出码门禁。后续项目环境创建、测试、数据生成与审计已验证该启动路径可用。

## D-MVP-11：预算聚合读取错误的 evidence_level（已解决）

## D-MVP-12：probe 未独立记录评估源码来源（已解决）

训练 run 记录训练提交，但旧 probe manifest 仅记录 scope、状态和结果路径。若训练后修复
评估代码，结果无法直接确定使用了哪个评估提交。新 probe manifest 和 metrics 会同时记录
评估源码状态、完整配置哈希、数据 manifest 哈希、协议哈希、训练提交和 checkpoint SHA-256；
formal probe 继续强制 clean 工作树。

## D-MVP-14：XOR 与拼接线性 probe 几何不相容（v2 已修复，训练待运行）

v1 把 `joint_graph` 定义为 `visual_key XOR text_key`，fused representation 则是两个独立
encoder 输出的拼接。任意线性打分都分解为图像项与文本项之和，无法系统性分离 XOR 的
两组组合。v1 smoke 的 complementary joint_graph 主比较停在相同的多数类水平。

v2 将 joint_graph 改为四分类 `2 * visual_key + text_key`。该联合状态可由两个 one-hot
块拼接后的多类线性分类器精确解码；数据审计增加固定权重几何检查，class count 同步改为 4。

## D-MVP-15：互补任务数量与两任务 Go 门槛不一致（v2 已修复，训练待运行）

v1 complementary 文本只提供 `text_key`，entity、predicate、direction 的附加文本条件
信息均为零，因此只有 joint_graph 一个互补任务。协议却要求至少两个互补任务同时通过。

v2 在 complementary 图像中保留真实 subject、把 object shape 替换为独立 nuisance，文本
提供真实 object；entity 因而成为第二个 fused 互补主任务。正式 complementary 门槛只统计
entity 与 joint_graph，predicate/direction 的偶然变化不能计入两任务通过数。

## D-MVP-19：训练数据管线在冻结前更换为 GPU 驻留后端（2026-08-03）

v1/v2 原训练路径使用 Windows 上 spawn 的 DataLoader worker 与逐样本 collate，是
D-MVP-4 悲观外推的主要来源。现新增 `training.data_backend` 配置
（`dataloader`/`gpu_resident`），`gpu_resident` 将一个 (condition, split) 的全部
shard 一次性驻留为设备张量（pilot 全量约 150MB/条件），按 seed 化 `randperm` 取
batch，语义上等价于原 `shuffle=True, drop_last=True` 契约但样本顺序与 DataLoader
采样器不逐位一致。同时新增 `training.precision`（`fp32`/`bf16`）与 `training.tf32`
开关；实测 bf16 无收益（见 D-MVP-4），两个配置均定稿为 `fp32` + `tf32: false`，
即数学语义与 v1 完全一致，本次变更只移除管线开销。该变更发生在协议冻结前，配置
哈希随之变化；数据段哈希不变，已生成的 v2 数据集不受影响。回归测试覆盖驻留张量
与 shard 数据逐元素一致性、seed 确定性和 CPU 路径的完整 train_run。

## D-MVP-20：held-out 排除规则边缘不均衡导致 pilot 数据审计失败（2026-08-04 已修复）

2026-08-04 pilot 数据首次生成后，oracle 审计以三条失败拒绝该数据集：complementary 的
image/text 单模态 entity 可辨识率 0.287/0.286 超过上限 0.268（理论 0.25 + 3 SE），
irrelevant 文本 entity 0.0754 超过上限 0.0728（理论 0.0625 + 3 SE）。

根因：v1/v2 沿用的排除规则 `(entity_label * 3 + predicate) % 5 == 0` 在 16 个 entity 上
命中不均——3 个 entity（e ≡ 2 mod 5）不排除任何 predicate，其余 13 个各排除 1 个。保留
组合上 entity 边缘因此不均匀（4/51 对 3/51），并使 subject 与 object 之间产生可利用的
条件相关。smoke 未检出仅因 64 条测试样本的 3 SE 上限过宽（0.41），属于检验功效不足，
不是审计误报；审计门禁在 pilot 规模按设计工作。

修复：改为边缘均衡规则 `(subject_shape + object_shape + predicate) % 4 == 0`，
`heldout_modulus` 由 5 改为 4。每个 (subject, object) 恰好排除 1 个 predicate，每个
(subject, predicate) 恰好排除 1 个 object，每个 (object, predicate) 恰好排除 1 个
subject；entity 边缘与单模态条件分布在保留组合上严格均匀，未见组合占潜在空间 1/4。
新增均衡性回归测试；用实际采样器在 pilot 规模（50k train + 5k test）做内存内 oracle
模拟，全部检查通过且余量充足（0.257 < 0.268、0.0636 < 0.0728），test seen/unseen 精确
对半。

证据处置：失败的 pilot 数据集 `...__654a4867e72a` 连同其 `audit_report.json` 保留为
缺陷证据，不删除。旧规则生成的 smoke 数据集 `...__2999e07bcae3` 与其上的 40 个 v2
smoke 训练 run 保留为工程链路验证证据；其研究数值本就不进入结论。规则变更进入源码，
配置哈希随 `heldout_modulus` 变化，新旧数据集物理隔离。协议冻结前该规则以本条与
协议 §10.3 为准。

## D-MVP-17：互补图文缺少 InfoNCE 共享锚点（v2 已修复，训练待运行）

v1 complementary 图像暴露 subject/predicate/direction/visual_key，文本只暴露 text_key，
图文正样本没有稳定共享变量。标准 image–text InfoNCE 因而缺少可学习的配对信号。

v2 让 predicate 与 direction 在两模态中保持真实可见，作为共享对齐锚点；它们对各自任务
是冗余信息。entity 仍由 image subject 与 text object 拆分，joint_graph 仍由 visual_key
与 text_key 拆分，因此两个互补主任务的条件信息契约不变。数据审计显式记录该锚点。

## D-MVP-18：probe metrics 与聚合器的 evidence_level 粒度不一致（已解决）

v1 probe metrics 把证据等级记录在同目录的 completed probe manifest，旧聚合器却尝试从
每条 metric row 读取该字段，正式聚合会触发 `KeyError`。聚合器现从 manifest 取得并校验
证据等级，再注入规范化记录；未来 metrics payload 顶层也显式携带该字段。回归测试和 v1
临时完整聚合演练均已通过。
